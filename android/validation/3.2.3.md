# Android 3.2.3 validation

Checked on 2026-10-20 in the same native Android 17 VM used for 3.2.2. Training sharing was off. All speech was synthetic. The speed change prepares AAC during recording, rather than doing that work after Stop.

## Exact audio codec comparison

An isolated Android application compiled the encoder from 3.2.2 beside the proposed live encoder. Each received identical PCM for six second, one minute, 130.47 second and ten minute workloads. Each implementation ran twice per workload, in baseline, candidate, candidate, baseline order. The candidate received a progressively written WAV at approximately 20 times normal recording speed; its timer below starts when that writer closes. The baseline timer covers its entire encoding pass on the finished WAV.

| Source duration | 3.2.2 encoding after input ends, median | Live encoder finish after input ends, median |
| --- | ---: | ---: |
| 6 s | 288 ms | 9 ms |
| 60 s | 1,553 ms | 9 ms |
| 130.47 s | 3,869 ms | 17 ms |
| 600 s | 14,788 ms | 13 ms |

For every workload, all four AAC files had the same SHA256 hash. All 16 files decoded without errors. This verifies that the tested scheduling change preserves the compressed audio exactly. The computation now overlaps recording; these numbers describe the remaining wait, not a reduction in total encoding computation or a battery measurement.

## Full application and public Cloud

The signed release application recorded the same one minute source through the emulator microphone, with Cloud, Normal style and English selected.

| Version | Stop to delivery | Capture stop | Encoding or adoption after Stop | Recognition | Formatting |
| --- | ---: | ---: | ---: | ---: | ---: |
| 3.2.2 | 4.780 s | 43 ms | 2,197 ms | 888 ms | 1,348 ms |
| 3.2.3, clean repeat | 2.797 s | 71 ms | 18 ms | 1,063 ms | 1,436 ms |
| 3.2.3, next take without restarting | 2.739 s | 47 ms | 6 ms | 1,000 ms | 1,481 ms |

The baseline and both clean candidate AAC files decoded to 61.632 seconds, including the harness's leading and trailing silence. The clean candidates reduced observed total latency by about 41–43%; most of that change was the removal of work after recording. This small sample does not establish a general Cloud latency guarantee.

The actual Windows Cloud engine processed the exact clean candidate AAC in 2.222 and 1.886 seconds, with the same language and formatting instructions. Android's 2.797 seconds is now close to that measured Cloud path, although device, network and server load still affect the result.

A 130.47 second source was also recorded at normal speed. The candidate captured 132.096 seconds including padding, decoded to 132.224 seconds, and delivered in 4.732 seconds after Stop: capture finish 68 ms, adoption 3 ms, recognition 1.861 seconds and formatting 2.636 seconds. This also exercises live encoding for longer than the former encoder's two minute total timeout. The stall guard now measures lack of progress instead of total recording duration.

An earlier candidate one minute capture contained 132.752 seconds of audio and was excluded from the speed comparison. Its 2.740 second delivery is not used as a matched result. A fresh application process produced the correct duration above. The cause of that anomalous capture has not been established.

## Failure handling and checks

The WAV is written on the microphone thread and remains recoverable after a process death. The codec uses an independent worker. Its final wait is bounded to one second; a failed or late result is discarded and the complete WAV is uploaded directly. No partial AAC is adopted. Cancellation removes the optional compressed temporary file together with the cancelled take.

The signed local build passed 121 tests with seven optional live tests skipped. New tests exercise completed output, codec failure and a codec that returns after its finish deadline. Release lint completed with no errors; the two existing warnings and one hint remain in unchanged UI code. Audio settings are unchanged: AAC LC, 16 kHz mono, 32 kbps.

Buffer polling follows the documented synchronous [MediaCodec API](https://developer.android.com/reference/android/media/MediaCodec). Input is supplied while available; the worker waits for output when it needs the codec to make progress or is finishing the stream.
